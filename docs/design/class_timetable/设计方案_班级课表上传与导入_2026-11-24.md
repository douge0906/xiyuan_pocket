# 班级课表上传与导入 · 设计方案

> 项目：掌上锡院（xiyuan_pocket + xiyuan_control + xiyuan_toolbox）
> 版本：v1.0 设计稿
> 日期：2026-11-24
> 交付范围：设计方案 + 成品 UI 设计图 + 交互逻辑说明（**不含业务代码实现**）

---

## 0. 一句话概述

给掌上锡院加一条**「锡院在线课表」**链路：同学可以按 **学年 → 学院 → 专业 → 班级** 检索并一键导入别人上传的班级课表（**直接覆盖**本机同名班级课表，导入前给出差异明细）；也可以把自己本机已有的课表上传上去，经过人工审核后发布，供同班同学使用。**一个班级允许多份课表并存**（不同上传者 / 不同来源 / 不同版本），每份课表独立走审核、独立被预览、独立被导入。

## 1. 背景与现状诊断

### 1.1 需求原文

> 为掌上锡院课表导入设计一个班级课表上传与导入的功能，班级导入带检索功能，上传需审核机制，一个班级可存在多份课表，结构按照学年 学院 专业 班级 划分，其他逻辑自拟，合理闭环即可。

拆成四条硬约束：

| # | 约束 | 落地口径 |
|---|---|---|
| C1 | 班级课表**上传** | 用户把自己的班级课表提交到服务端 |
| C2 | 班级课表**导入** + **检索** | 用户能搜到别人上传的课表并导入本机 |
| C3 | 上传需**审核机制** | 人工审核 + 状态机 + 审计留痕 |
| C4 | **一个班级多份课表** | 班级是容器，课表是版本，同班可有 N 份 |
| C5 | 结构按 **学年 / 学院 / 专业 / 班级** 划分 | 四段级联 |

#### 完全没有的（本次设计要新建）

1. **服务端没有班级课表上传接口**，也没有任何课表相关数据表（`db.py` 建表清单里没有）。
2. **没有课表审核状态模型**：`resource_uploads` 是教材语义（course_name / book_name / area），没有 `bh_id / xnm / xqm`，更没有课程明细表。
3. **客户端没有「班级实体」模型**：`bh_id / jgmc / zymc / njdm_id / xkrs` 只在 `class_picker_page.dart` 的 Map 里临时存在，取完课表就丢（`:161-162` 只回传 `className` + `courses`）。
4. **客户端没有从服务端拉取他人课表的入口**：`ApiService` 里班级相关方法只有 `searchClassList` / `fetchClassSchedule`，两者都是**直连教务**。
5. **导入没有审核中间态**：`CourseTable.kind` 只有 `own/imported/manual`，没有 `uploaded/pending/approved`。
6. **课程字段有三套命名**：`course_fetcher` 9 键 snake_case / `class_timetable` 7 键 snake_case / `course_pdf_import` 7 键 camelCase —— 新接口必须收口到一套。

### 1.3 三个真正的设计难点

**难点 A：归属四段里，「学院」和「专业」没有稳定 ID。**
教务班级行只给 `jgmc`（学院名）/ `zymc`（专业名）/ `bj`（班名）/ `njdm_id`（年级码），**没有学院 ID、没有专业 ID**。所以「同一个班级」不能靠 ID 判定，只能靠 **(学年, 学院名, 专业名, 班名)** 四元组。班名本身在跨学院时可能重名，必须把学院名带进键里。

**难点 B：一个班级一份权威课表 vs. 多份课表并存。**
教务系统里一个班的课表是**唯一**的，但锡院在线课表里一个班可能有多份上传（学生 A 上传 28 门、学生 B 上传 26 门、有人更新成了新版本）。如果不做版本语义，在线课表会变成「一堆互相矛盾的数据」。

**难点 C：导入的资料是「别人的」，而上传来源如果放开就会失控。**

如果允许「上传 PDF」「拍照 OCR」「教务实时抓取」多种来源，审核员要面对大量需要逐条核对的内容，审核成本会失控，审核质量也会崩。

**本次的解法是收口而不是分级**：上传来源只保留「从本机课程表导入」「从本机导出的文件导入」两种 —— 两者都是**用户本机已经存在的真实课表**，可信度天然一致，审核只需比对结构与一致度，不必再为 PDF/OCR 单独设计逐条人工核对的通道。这样审核成本可控、审核质量不塌，也让「锡院在线课表」里的每份表都源自某个同学的真实课表。

## 2. 设计原则

| 原则 | 含义 | 在本设计中的体现 |
|---|---|---|
| **P1 复用优先** | 不自造与现有系统平行的一套 | 审核端点形状照抄 `resource_uploads`；outbox 沿用同一套 worker 范式；客户端落库走 `CourseStorage.createTable` / 覆盖走同表替换 |
| **P2 令牌唯一** | 不新造颜色/圆角/字号 | App 端沿用 `app_theme.dart` + `cprint_scan_mockup.html`；后台沿用 `admin_ui.py` 的 `:root` |
| **P3 单一数据源** | 检索页只给一个可信来源 | 检索页只查「已审核发布」的锡院在线课表库；教务实时路径保留在「输入账密快速导入」里，不与在线课表库并列 |
| **P4 可解释** | 任何差异都告诉用户差在哪 | 每份课表带「与教务一致 N/M」；导入前给差异明细（新增/变更/移除）；审核端给并排比对 |
| **P5 最小暴露** | 不上传任何个人隐私 | 只上传课程级信息（课程名/教师/教室/节次/周次）+ 一个自拟**上传者名称**（≤16 字，非学号/手机号）；账号身份不随课表公开 |
| **P6 不破坏存量** | 导入的班级课表绝不能被「我的教务」同步覆盖 | 复用 `kindImported` + `syncableByMyCampus`；在线课表导入只覆盖 `kindImported` 同名表，**永不覆盖 `kindOwn`** |
| **P7 有闭环** | 每条路都要能走完 | 搜不到 → 引导上传 → 审核 → 发布 → 被预览 → 被导入（覆盖）→ 被举报/下架，全链路有出口 |

## 3. 领域模型与信息架构

### 3.1 五层结构

```
学年学期  (academic_term)          xnm + xqm  →  "2026-2027 第1学期"
  └─ 学院  (college)               jgmc 名称  →  "智能工程学院"
      └─ 专业 (major)              zymc 名称  →  "电气工程及其自动化"
          └─ 班级 (class)         bj 名称 + njdm_id → "25电气1班"
              └─ 课表 (timetable) 一份份上传的课表，N 份并存
```

**为什么用名称而不是 ID 做键：** 教务侧只有名称。学院/专业名称在无锡学院内部是稳定的（没有同名学院），所以用「学年 + 学院名 + 专业名 + 班名」四元组做自然键，是唯一既能对齐教务、又不引入新字典维护成本的做法。后续若学校开放稳定 ID，可在不破坏既有数据的前提下加一列 `external_id` 做映射。

### 3.2 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `AcademicTerm` | `xnm`(2026) / `xqm`(3,12,16) / `label` | 复用现有 `showSemesterPicker` 的编码口径 |
| `ClassRef` | `xnm, xqm, jgmc, zymc, bj, njdm_id, xkrs` | 客户端新增的**班级实体**（现在只有散落的 Map） |
| `TimetableUpload` | `id, device_id, uploader_name, class_ref(4段), source, version, course_count, status, review_note, created_at, reviewed_at, diff_summary` | 一份上传 = 一个班级下的一份课表 |
| `TimetableCourse` | `name, teacher, classroom, weekday, start_slot, end_slot, weeks` | 课程明细（服务端存的规范化 7 键） |
| `TimetableVersion` | 同一 `class_key` 下的 `v1 / v2 / ...` | 同一提交者对同一班级的多次提交会累版本；不同提交者各自独立起版本线 |

### 3.3 一个班级多份课表 —— 版本语义（解决难点 B）

规则：

1. **班级是容器**：`(xnm, xqm, jgmc, zymc, bj)` 唯一确定一个班级，班级下挂 N 份课表。
2. **每份课表有独立的来源**（**只有两种，都以本机真实课表为准**）：
   - `source = local_table`（从本机课程表导入）→ 可信度 `high`
   - `source = local_file`（从本机导出的文件导入）→ 可信度 `high`
   - 两种来源都经过「课程结构完整 + 与基准一致度」两道检查，审核通道一致（都是快通道），差别只在取数路径。
3. **版本号按提交者分组**：`v1 / v2 / v3…` 只在**同一提交者 + 同一班级**内递增；不同人上传同一班，第一份是 v1，第二份也是 v1 但归属不同人。
4. **在线课表展示不做「唯一正确版」**，而是**按一致性排序**：与教务基准一致度高的排前面，附「与教务一致 26/28」的标签。
5. **一份被下架不影响同班其他版本**。
6. **版本卡面上只放三个小字**：课程数 / 上传时间 / 上传者 —— 来源与一致度放在详情里，避免卡片信息过载。

## 4. 两级状态机

### 4.1 上传审核状态机（沿用 `resource_uploads` 四态，语义对齐）

```
                 ┌───────────── 审核人下架（removed）─────────────┐
                 │                                                │
   [提交] ──▶ pending ──▶ approved ──▶ (发布队列 job) ──▶ 已发布   │
            待审核      已通过                                  │
                 │                                                │
                 └──▶ rejected ──▶ 修改后重新提交（回到 pending）─┘
                            已驳回
```

| 状态 | 客户端文案 | 含义 | 客户端可见性 |
|---|---|---|---|
| `pending` | 待审核 | 已提交，等审核 | 自己可见；他人不可见 |
| `approved` | 已通过 / 已发布 | 审核通过，**发布是异步的**（进 outbox 队列） | 自己可见；发布完成后他人可见 |
| `rejected` | 已驳回 | 附驳回原因与意见 | 自己可见（仅自己）；他人不可见 |
| `removed` | 已下架 | 审核通过后又被下架（学期过期 / 举报 / 数据错误） | 自己可见（保留记录）；他人不可见 |

**关键规则：**

- **提交即 `pending`**，服务端不接受客户端直接指定状态（照抄 `api.py:1177-1183` 的固定 `status='pending'`）。
- **审核动作只能走 `PATCH /admin/timetables/{id}/status`**，body 只允许 `approved / rejected / removed` 三值，非法值报 `invalid_status`（照抄 `admin.py:549-556`）。
- **审核通过 ≠ 已发布**：先写 `timetable_publish_jobs`（outbox），worker 消费后才在客户端可见。客户端「我的上传」页在 `approved` 但未发布时显示「审核通过 · 发布中」。
- **`rejected` 必须带原因**（结构化原因码 + ≤500 字意见），否则审核员无法给出可执行的驳回。
- **每次状态变更写 `audit_logs`**（action = `timetable_approved` / `timetable_rejected` / `timetable_removed`）。

### 4.2 课表版本状态机（客户端本地）

```
  （从锡院在线课表导入）
  [不存在] ──▶ imported  ──▶ 使用中 ──▶ 用户可重命名 / 删除
                 │
                 └──▶ 本机已有同名班级课表 → 覆盖确认（差异明细）→ 整表替换
```

复用 `CourseTable.kind`：

| kind | 用途 | 会被「我的教务」同步覆盖吗 |
|---|---|---|
| `own` | 用户自己的课表 | ✅ 会 |
| `imported` | **从锡院在线课表导入的班级课表** | ❌ 不会（`syncableByMyCampus`） |
| `manual` | 手工新建 | ❌ 不会 |

> 本设计**不新增** kind 值。导入的班级课表继续用 `kindImported`，直接继承现有的同步隔离规则（P6），避免改动 `resolveSyncTargetId` 的判定逻辑。
>
> **覆盖的目标只能是 `kindImported` 的同名班级课表。** 用户自己的 `kindOwn` 课表（教务同步来的权威数据）永远不被在线课表替换 —— 在线课表数据可以替换「在线课表来的那份」，不能替换「你自己的那份」。

### 4.3 重复提交与版本并存

同一个班级重复上传时：

- **同一提交者 + 同一班级 + 同 `source`** → 自动升版本 `v1 → v2`，旧版本转 `superseded`（客户端不展示，但留档）。
- **不同提交者 + 同一班级** → 各自独立成一份，**都保留**，详情页的「班级课表」区块并列展示为多张等宽版本卡，每张卡带自己的上传者名称。
- **同一提交者 + 同一班级 + 不同 `source`** → 视为两份独立来源，并列展示；系统**不自动合并**。

**与「导入直接覆盖」的关系（两处覆盖语义不同，别混）：**

| 场景 | 动作 | 说明 |
|---|---|---|
| 用户**上传**同一班的第二份 | 服务端**并存**（升版本或并列） | 在线课表侧要保留多份，因为来源与上传者不同，可能各有对错 |
| 用户**导入**别人的课表到本机 | 客户端**覆盖**本机同名班级课表 | 本机只需一份权威版本，用户要的是「现在就用这份」 |

即：**在线课表多份并存，本机一份覆盖**。这两条同时成立才是闭环。

## 5. 功能模块设计

### 5.1 班级课表检索页

**入口（两条，闭环）：**

1. **课表页 → 右上角「导入」按钮 →「导入课表」面板 →「锡院在线课表」**（主入口）。课表页右上角是 `Icons.file_download_outlined`（tooltip「导入课表」），点击打开现有 `_CourseImportSheet`（`lib/pages/course_import_sheet.dart`）；本方案在该面板里**新增一行「锡院在线课表」**，位置排在「从图片识别导入」之后、「导入掌上锡院专属方案」之前，图标用 `Icons.school_rounded`，行下附一行说明「按班级检索已上传并审核通过的课表，导入后覆盖本机同名班级课表。」
2. **服务 tab → 锡院在线课表**（次入口，直接落到检索页）。

**单一数据源（决策）：** 检索页**不再有「锡院在线课表库 / 我的教务（实时）」分段控件**，只保留一个数据源 —— **已审核发布的班级课表库**（服务端 `GET /api/v1/timetables/search`）。

理由：
- 教务实时抓取要求用户绑定教务账号，且会把「谁的课表」和「别人传的课表」混在一屏，分不清可信度；
- 分段控件让首屏多一层无信息量的切换，挤掉了搜索栏的位置；
- 教务实时路径**并未删除**，它仍存在于「课表页 → 导入课表面板 → 从教务系统导入」与「导入一份新课表 → 输入账密快速导入」这两条老路上，只是不再作为检索页的并列数据源。

> 兜底：若某班从未有人上传，检索页会给明确出口 ——「上传本班课表」，走 §5.4 上传向导，审核通过后同学即可检索到。**这条路径闭合了「没有课表 → 谁来提供」的死结。**

**筛选：四段级联**

```
学年学期 ▸ 学院 ▸ 专业 ▸ 班级
```

- 学年学期是**首个 chip，且可更改**：点击打开滚轮/列表选择器（复用 `course_storage.dart` 的 `semesterArgsFor` / `_semesterOptions` 口径），切换学期后检索结果、列表计数、课表版本都按新学期重新加载；已选学期的 chip 用虚线边框 + 下箭头，提示「可改」。
- 学院 / 专业 / 班级三个 chip 常驻，点击打开 **bottom sheet**（不逐级跳页，减少跳出成本）。
- sheet 顶部四行**联动选择器**（学年 → 学院 → 专业 → 班级），下方是当前可选值的单选列表 + 班级数。
- **联动规则**：选学院后专业列表刷新；选专业后班级列表刷新；**改上级则下级自动清空**（照抄 `class_picker_page` 的 `_grades` / `_colleges` 去重排序思路）。
- 在线课表库只列出「已有人上传过课表的学院/专业/班级」；未上传过的班级不出现在列表里，只能靠搜索或「上传本班课表」补齐。

**关键字**：与既有 `class_picker_page` 口径一致 —— 匹配 **班名 / 专业 / 学院** 三字段，小写包含。搜索栏置顶（AppBar 之下第一屏），提示语沿用「搜班名 / 专业 / 学院，例如：25安工」。

**班级卡片字段：**

```
25电气1班
电气工程及其自动化 · 智能工程学院
[2 份课表]  ·  28 门  ·  一致 26/28  ·  2 小时前        [32 人]  ›
```

- `N 份课表`：绿底小标签 —— 「该班存在多份课表」的一级信号，点了进详情页才做多版本选择
- `N 门`：该班最新一份的课程数
- `一致 26/28`：与教务基准的一致度，绿（全一致）/ 橙（部分差异）
- 时间：相对时间（「2 小时前」）
- 人数 pill：灰底 + primary 文字，与教务班级人数一致

**空态闭环：** 搜不到时明确告诉用户原因，并给出出口 ——「该班还没有同学上传过课表。你可以先上传一份，审核通过后同学就能查到。」+ 主按钮「上传班级课表」+ 次按钮「重置筛选」。

### 5.2 班级课表详情页

**结构：三段，自上而下（用户明确指定）**

```
① 班级基础信息
② 班级课表（可存在多版本）
③ 课程预览（跟随 ② 实时切换）
```

#### ① 班级基础信息

一张白卡，四行键值对（顺序与上传时填写顺序对齐）：

```
学年学期   2026-2027 第1学期
学院       智能工程学院
专业       电气工程及其自动化
班级       25电气1班
```

- 键列 66px 灰字（沿用 `.kv .k`），值列 13.5px 半粗（沿用 `.kv .v`）。
- 右侧竖排一行操作：`收藏`（次要）+ `导入到我的课表`（主按钮，实心，固定在底部操作栏，滚动时常驻）。

#### ② 班级课表（多版本）

- 区块标题 `班级课表` + 计数 `2 份` + 副标题「同一班级可有多份上传，选一份预览」。
- **版本卡等宽排列**（两列 grid，等宽等高，超出文字省略号，不换行撑高）：
  - 卡头：版本号 `v2`（选中态 primary 文字）+ 状态角标 `预览中`（选中）/ `已发布`（未选中）。
  - 卡身三行，**只放三要素**（用户明确要求「小字只有课程数和上传时间和上传者」）：
    - `28 门课`
    - `2 小时前`
    - `张同学`
  - 选中态：primary 8% 底 + primary 描边（照抄 `course_table_home_page` 的 `_conflictOption` 选中视觉）；未选中：白底 + 6% 黑贴边微影。
  - **来源只在 tooltip/详情里给**，不占卡面空间（卡片视觉保持等宽整齐）；来源取值只有两种：`从本机课程表导入` / `从本机导出的文件导入`。
- 点任一版本卡 = **切换预览**（不是直接导入）。课程预览区随之刷新，标题变成 `课程预览 v2 · 28 门`。
- 版本卡按「提交时间倒序」排列，最新在最前。

#### ③ 课程预览

- 标题 `课程预览 v2 · 28 门`，随选中版本实时切换（不重新进页面）。
- 按星期分组（周一 ~ 周日），每门课一行：彩色左边条（`coursePalette` 浅色）+ 课程名 + `第N-M节` + `教师` + `@教室` + `周次`。
- **周次表达**：`1-16周`、`1-8周,10-16周`（复用 `parseWeeks` / `formatWeeks` 的能力，不新造格式）。

**收藏**（本次新增的小闭环）：把某个班级的某份课表加入收藏，收藏列表在「我的上传」页并列展示。因为在线课表数据会变动，收藏的是**引用**不是副本。

### 5.3 导入确认 sheet（导入链路的关键一屏）

用户点「导入到我的课表」后弹出的底部弹层：

1. **课表名称**（默认 `25电气1班`，可改）
2. **学年学期**（默认该课表的学年学期，可改 —— 允许导入到别的学期，但要提示）
3. **覆盖提示**（橙色）：「将覆盖你已有的「25电气1班」课表。」
4. **差异明细**（键值三行，把「差在哪」说清楚）：
   ```
   新增课程   2 门   大学物理实验Ⅱ、模拟电子技术
   变更课程   1 门   数字电子技术（第9-10节 → 第7-8节）
   移除课程   1 门   形势与政策
   ```
5. **结果提示**（灰色 info）：「本地该班课表会被替换。其他班级和其他学期的课表不受影响。」
6. **主按钮**「覆盖并导入」。

**关键设计：直接覆盖。** 用户明确要求「导入到我的课表直接覆盖，可提示差异性」。落地规则：

- 命中的目标 = **本机已有的同名班级课表**（`CourseTable.kind == kindImported` 且归属四段与所选课表一致），命中则**整表替换**该表内容，并把 `semesterStart` 同步为所选课表的学期起点。
- 若本机没有该班的课表 → 走**新增**分支（等价 `createTable(kind: kindImported)`），此时不显示覆盖提示，只显示「将新增一份「25电气1班」课表」。
- **不按课程逐条合并、不做自动去重**：整体替换，行为可预期。差异明细只做「告知」，不做「询问」。
- 覆盖后必须执行既有联动三件套（见 §7.1）：切表 → `courseProvider.notifier.load()` → `WidgetSyncService.syncTodayCourses()` + `CourseReminderService.rescheduleAll()`。
- 覆盖是**破坏性操作**，所以按钮文案用「覆盖并导入」而不是「导入」，橙色 banner 放在按钮正上方，避免误触。

### 5.4 上传课表（3 步向导）

#### Step 1 · 归属与来源

- **归属信息**（四行 pick 行，带必填红星）：学年学期 / 学院 / 专业 / 班级。
  - 学年学期：滚轮选择器，复用 `_semesterOptions` / `_parseSemesterOption` 口径。
  - 学院 / 专业：可搜索的下拉（在线课表库已出现的学院列表优先，本地缓存）。
  - 班级：**「选择或输入班名」** —— 既可从在线课表库已知班级里选，也可直接手输（「老师通知的班名和系统不完全一致」是常态）。
- **课表来源**（**两选一**，整宽行卡）：
  | 来源 | 说明 | 可信度 | 审核策略 |
  |---|---|---|---|
  | **从本机课程表导入** | 直接读取你本机课表页里已有的那份课表（含课程名、教师、教室、周次） | high | 快通道：只做差异比对 |
  | **从本机导出的文件导入** | 读取本机导出的课表文件（`course_transfer_service` 的 `xiyuan.course.tables` schema，JSON 格式） | high | 快通道：只做差异比对 |

  两种来源都**以本机已有内容为准**，不存在「从教务现抓」和「拍照识别」这类低可信度入口 —— 这正是审核成本可控的前提。
- 页脚提示：「课程内容与教务系统核对一致时，审核通常 1 个工作日内完成。」

#### Step 2 · 课程核对

- 顶部告警条：「已解析 28 门课程，2 处需要你确认」（橙底，warning 色系）。
- 课程清单按星期分组，每行：`课程名` + `第N-M节 时间` + `教师` + `@教室` + `周次`。
- **问题课程高亮**（橙色描边 + 角标）：
  - `周次待确认` —— 周次缺失或解析异常
  - `时间重叠` —— 与另一门课时间冲突（例：复变函数与积分变换 与 大学物理实验Ⅱ 冲突）
  - `缺少教室` —— 地点为空
- 点课程 → 打开**整页编辑**（复用 `showCourseFormSheet`），改完即时回到清单。
- 底部：`添加课程`（次要）+ `下一步：提交审核`（主按钮）。

#### Step 3 · 提交审核

- **归属与来源摘要卡**（回显四段 + 来源 + 版本号 v1）。
- **上传者名称**（**必填**，新增字段）：
  - 输入框，占位符「填一个同学都认得的名字，例如：张同学」。
  - 限制：**最多 16 字**；不得包含学号（连续 6+ 位数字）、手机号（11 位数字）、真实姓名（无法自动判定，靠提示与审核拦截）。
  - 用途：这个名字会显示在班级课表的版本卡上（小字三要素之一），让同学知道「这份表是谁传的」，建立信任。
  - **默认建议**：可带出本机已有课表的名称（`CourseTable.name`）作为预填，减少输入成本，但用户可改。
  - 服务端只存这一个显示名 + 账号标识，**不随课表公开账号身份**。
- **隐私自检卡**（绿底「通过」）：
  - ✓ 上传者名称不含学号、真实姓名、手机号
  - ✓ 课程内容不含成绩、作业与通知内容
  - ✓ 账号身份不随课表公开，仅以你填写的名称展示
- **补充说明**（选填 textarea）：占位符「例如：第 8 周起班级换教室，已按最新通知更新。」
- **同意勾选**：「我确认该课表为班级公开信息，不包含个人隐私，并同意平台在审核与展示中以我填写的「上传者名称」展示贡献者。」
- **提交按钮**「提交审核」。

### 5.5 我的上传（审核状态跟踪）

**列表**：状态分组 chips（全部 / 待审核 / 已通过 / 已驳回 / 已下架）+ 数量。

## 6. 服务端设计（接口契约）

### 6.1 放在哪个服务

**结论：放在 `xiyuan_control`（运营后台所在服务），不放 `xiyuan_toolbox`。**

理由：
1. 运营后台 `xiyuan_control` 已有 `require_admin` 鉴权、`audit` 审计、`resource_jobs` outbox、SQLite 表结构与迁移工具（`_ensure_column`），是审核类资源的天然归宿。
2. `xiyuan_toolbox` 的班级课表接口（`/api/v1/course/class/search`、`/api/v1/course/class/schedule`）是**客户端直连教务的代理**，它的管理员鉴权是 `X-Admin-Key`，与 control 侧的 `Authorization: Bearer` **互不通用**；把审核态塞进去会造成第三套鉴权。
3. 客户端已有稳定的 control 通道（`ControlConfig.baseUrl` + 设备断言），资源中心与「我的上传」都在这条链路上，新增课表链路**沿用同一条**，不引入第二个服务端地址。

### 6.2 客户端可见端点（`/api/v1/...`）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/v1/timetables/search` | 设备令牌 | 按四段（含可更改的学年学期）+ 关键字检索**已发布**的班级课表；返回班级聚合列表 + 每个班级的份数 |
| GET | `/api/v1/timetables/class/{class_key}` | 设备令牌 | 取某班级下的全部已发布课表（多份并列），含课程明细 + 上传者名称 + 一致度 |
| POST | `/api/v1/timetables/uploads` | 设备令牌 | 提交上传（归属四段 + 来源 + **上传者名称** + 课程明细），服务端固定 `status='pending'` |
| GET | `/api/v1/timetables/uploads/mine` | 设备令牌 | 我的上传列表（含状态、审核意见、版本号、上传者名称） |
| DELETE | `/api/v1/timetables/uploads/{id}` | 设备令牌 | 撤销自己处于 `pending` 的上传 |
| POST | `/api/v1/timetables/uploads/{id}/resubmit` | 设备令牌 | 驳回后修改重提（升版本号） |
| GET | `/api/v1/timetables/favorites` | 设备令牌 | 收藏列表 |
| POST/DELETE | `/api/v1/timetables/favorites/{class_key}` | 设备令牌 | 收藏 / 取消收藏 |

**上传请求体关键字段**（`POST /api/v1/timetables/uploads`）：

```json
{
  "xnm": "2026", "xqm": "3",
  "jgmc": "智能工程学院", "zymc": "电气工程及其自动化", "bj": "25电气1班",
  "njdmId": "2025",
  "source": "local_table",
  "uploaderName": "张同学",
  "courses": [
    {"name": "大学物理实验Ⅱ", "teacher": "朱弘桢", "classroom": "C2",
     "weekday": 3, "startSlot": 3, "endSlot": 4, "weeks": "1-16周"}
  ],
  "note": "第 8 周起换教室"
}
```

**字段约束**：

| 字段 | 约束 | 校验点 |
|---|---|---|
| `source` | 枚举，**只有两个值**：`local_table`（从本机课程表导入）/ `local_file`（从本机导出的文件导入） | 服务端拒绝其它值（400 `invalid_source`） |
| `uploaderName` | 必填，1–16 字，去首尾空格；不得含 6 位以上连续数字（疑似学号）或 11 位手机号 | 服务端 400 `invalid_uploader_name`；命中疑似学号/手机号直接拒绝，不做静默替换 |
| `courses` | 1–200 条（对齐 `course_transfer_service` 的 `maxCourses=2000` 上限，取更严的 200）；字段名沿用**服务端既有 snake_case 7 键**（`name/teacher/classroom/weekday/start_slot/end_slot/weeks`） | 单条字段缺失用默认值，课程名不可为空 |
| `weeks` | 文本，原样存 `1-16周` 这类写法 | 解析失败按「每周都上」处理，与 `parseWeeks` 语义一致 |

**统一响应格式**：沿用 `xiyuan_control` 的信封 `{"error":{"code","message"},"request_id"}`（`api.py:43-44` + `main.py:102-118`），不要用 toolbox 那套 `{"detail":"..."}`。

**可见性闸门**：在线课表检索与详情**只查 `status='approved' AND published=1`**。`pending` / `rejected` / `removed` 对他人一律不可见（照抄 `api.py:1274` 的 `WHERE u.status='approved'` 闸门）。

### 6.3 后台审核端点（`/admin/...`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/timetables?status=&xnm=&xqm=&keyword=` | 审核列表。状态白名单 `pending/approved/rejected/removed`，非法 → `fail(400,"invalid_status", ...)`；排序 `CASE status WHEN 'pending' THEN 0 ELSE 1 END, id DESC LIMIT 500` |

| GET | `/admin/timetables/queue` | 发布队列：pending/running/done/failed 计数与最近任务（照抄 `admin.py:650-674`） |

**驳回原因码**（结构化，便于客户端展示与统计）：
`mismatch_with_campus`（与教务基准差异过大）/ `incomplete_info`（课程信息不完整）/ `duplicate`（与已有课表重复）/ `personal_info`（疑似含个人信息）/ `wrong_class`（归属班级有误）/ `other`。

### 6.4 数据表（新建，沿用 `db.py` 的 `CREATE TABLE IF NOT EXISTS` + `_ensure_column` 迁移风格）

```sql
-- 一份上传 = 一个班级下的一份课表
CREATE TABLE IF NOT EXISTS timetable_uploads (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id       INTEGER NOT NULL,
    contributor     TEXT NOT NULL DEFAULT '',   -- 账号标识（仅用于归属与撤销，不对外展示）
    uploader_name   TEXT NOT NULL DEFAULT '',   -- 上传者名称（对外展示，≤16 字，非学号/手机号）
    xnm             TEXT NOT NULL,              -- 学年码 2026
    xqm             TEXT NOT NULL,              -- 学期码 3/12/16
    jgmc            TEXT NOT NULL,              -- 学院
    zymc            TEXT NOT NULL,              -- 专业
    bj              TEXT NOT NULL,              -- 班级
    njdm_id         TEXT NOT NULL DEFAULT '',   -- 年级码
    source          TEXT NOT NULL,              -- local_table / local_file（仅两种）
    version         INTEGER NOT NULL DEFAULT 1,-- 同提交者同班级内递增
    course_count    INTEGER NOT NULL DEFAULT 0,
    diff_matched    INTEGER NOT NULL DEFAULT 0,-- 与教务基准一致的课程数
    diff_total      INTEGER NOT NULL DEFAULT 0,-- 参与比对的课程数
    note            TEXT NOT NULL DEFAULT '',
    status          TEXT NOT NULL DEFAULT 'pending', -- pending/approved/rejected/removed
    review_note     TEXT NOT NULL DEFAULT '',
    review_reason   TEXT NOT NULL DEFAULT '',
    created_at      TEXT NOT NULL,
    reviewed_at     TEXT,
    published_at    TEXT
);
CREATE INDEX IF NOT EXISTS idx_timetable_uploads_status ON timetable_uploads(status, id);
CREATE INDEX IF NOT EXISTS idx_timetable_uploads_class  ON timetable_uploads(xnm, xqm, jgmc, zymc, bj);

-- 课程明细
CREATE TABLE IF NOT EXISTS timetable_courses (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    upload_id    INTEGER NOT NULL,
    name         TEXT NOT NULL,
    teacher      TEXT NOT NULL DEFAULT '',
    classroom    TEXT NOT NULL DEFAULT '',
    weekday      INTEGER NOT NULL,             -- 1..7
    start_slot   INTEGER NOT NULL,
    end_slot     INTEGER NOT NULL,
    weeks        TEXT NOT NULL DEFAULT '',
    FOREIGN KEY (upload_id) REFERENCES timetable_uploads(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_timetable_courses_upload ON timetable_courses(upload_id);

-- 收藏
CREATE TABLE IF NOT EXISTS timetable_favorites (
    device_id  INTEGER NOT NULL,
    class_key  TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (device_id, class_key)
);

-- 发布队列（outbox）
CREATE TABLE IF NOT EXISTS timetable_publish_jobs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    upload_id   INTEGER NOT NULL,
    action      TEXT NOT NULL,                 -- publish / unpublish
    status      TEXT NOT NULL DEFAULT 'pending',-- pending/running/done/failed
    attempts    INTEGER NOT NULL DEFAULT 0,
    last_error  TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    next_run_at TEXT NOT NULL
);
```

**为什么不建附件表：** 来源只有「本机课程表」和「本机导出的文件」两种，**文件在客户端就被解析成结构化课程了**，服务端只收结构化行，不收 PDF/图片二进制。因此 P0 不需要 `timetable_files` 表与对象存储链路 —— 这也是审核成本能压住的原因（审核员看到的是渲染好的课程表，不是要下载附件再比对）。若将来要支持「上传 PDF 原件」，再加表和 `object_storage` 的写入。

> `timetable_publish_jobs` 与 `resource_publish_jobs` 结构同构，但**独立建表**：`resource_jobs.enqueue` 的 action 白名单硬编码为 `("publish","delete")`，且 worker 分支硬编码调用 `_publish_resource_files` / `_delete_resource_objects`。课表没有文件对象，发布逻辑不同，硬塞进现有表会导致两套业务互相污染。**新建平行表 + 复用同一套 worker 范式**是最小改动。

### 6.5 与教务基准的比对

审核详情页的「上传内容 vs 教务基准」并排比对，是这个功能**最有价值的一块**：让审核员 3 秒内判断这份表能不能发。

比对规则（按课程四元组匹配）：

```
匹配键 = (课程名归一化, weekday, start_slot, end_slot)
```

| 情况 | 判定 | 展示 |
|---|---|---|
| 键相同，weeks/teacher/classroom 全同 | 一致 | 绿底 + 左绿条 |
| 键相同，weeks 或 teacher 或 classroom 不同 | 差异 | 红底 + 左红条，标出具体差异字段 |
| 上传有、教务无 | 多出 | 红底 + 左红条，标「教务无此安排」 |
| 教务必、上传无 | 缺失 | 红底 + 左红条，标「上传缺失」 |

汇总：「共 28 门，匹配 26 门，差异 2 门」。

**基准从哪来？** 两条路：
1. **上传时随请求附带** —— 客户端如果本机同时有该班的教务课表，可把基准一并带上（`campusBaseline` 字段，可选）。最省事，直接算。
2. **审核时服务端现抓**（`get_class_courses`）—— 需要教务凭据，成本高。**默认不做**，只在审核员点「拉取教务基准」时按需触发（限流 20/min，同 `class/search`）。

**没有基准时怎么办：** 因为上传来源已收敛为「本机课程表 / 本机导出的文件」，两种来源的课程内容都来自真实教务数据，只是不一定带基准。所以**一致性指标是可选的**：拿不到基准时，一致度显示「未比对」，审核员仍可按「课程结构完整、无个人信息、与同班其他版本是否冲突」判断。若同一班已有另一份已发布版本，则以**已发布版本**为对照基准（省一次抓取）。

## 7. 客户端落库与联动

### 7.1 导入锡院在线课表（直接覆盖）

**第一步：算差异。** 拿服务端返回的课程明细与本机同名班级课表做逐课比对，产出三类计数：

```
新增课程   = 服务端有、本机无
变更课程   = 两边都有，但 (weekday, startSlot, endSlot, weeks, teacher, classroom) 任一不同
移除课程   = 本机有、服务端无
```

差异明细要展示到课程名级别（如「数字电子技术（第9-10节 → 第7-8节）」），不能只给数字。

**第二步：覆盖或新增。**

```
GET /api/v1/timetables/class/{class_key}
  → 命中本机已有同名班级课表（kind==kindImported 且归属四段一致）
      → 整表替换 courses + semesterStart
      → 保持同一个 CourseTable.id（不新建表，不产生第二份）
  → 未命中
      → CourseStorage.createTable(
            name: 用户填的名称,
            courses: 课程明细 → Course 列表,
            semesterStart: 由学年学期推算的第 1 周周一,
            semesterStartSource: CourseTable.srcUser,
            kind: CourseTable.kindImported,      // ← 关键：不参与教务同步
         )
  → courseProvider.notifier.load()
  → WidgetSyncService.syncTodayCourses()
  → CourseReminderService.rescheduleAll()
```

**完全照抄 `course_table_home_page.dart:2544-2563` 的既有班级课表导入落库路径**，只是数据源从「直连教务」换成「服务端课表库」，并且在命中同名表时**替换而不是新增**。

**覆盖的边界（必须守住）：**
- 只覆盖 `kindImported` 且归属四段（学年/学院/专业/班级）完全一致的表。**用户自己的 `kindOwn` 课表（我的教务同步来的）永远不被覆盖** —— 那是权威数据，在线课表不该改它。
- 覆盖后该表的 `semesterStart` 与 `semesterStartSource` 同步更新为所选课表的学期起点。
- 覆盖不触碰其它班级、不触碰其它学期、不触碰课表外观设置。
- 覆盖是整表替换，**不做逐条合并**；差异提示只告知，不询问。

**课程 id 规则**：沿用 `cls_${bhId}_$wd-$start` 的思路，在线课表用 `cls_${uploadId}_$wd-$start`，保证同一份课表内 id 唯一且可追溯。覆盖时整表替换 id，不做新旧 id 的混合。

**课程字段映射**（服务端规范化 7 键 → 客户端 `Course`）：

| 服务端 | 客户端 |
|---|---|
| `name` | `name` |
| `teacher` | `teacher` |
| `classroom` | `classroom` |
| `weekday` | `weekday` |
| `start_slot` | `startSlot` |
| `end_slot` | `endSlot` |
| `weeks` | `weeks`（`parseWeeks` 口径） |

颜色：客户端用 `colorForName(name)` 本地派生（不传颜色，服务端也不存颜色 —— 避免两端配色漂移）。

### 7.2 上传提交

```
客户端 Step2 课程核对（用本地 Course 模型）
  → 归一化为服务端 7 键 snake_case
  → 附上 uploaderName（上传者名称）与 source（local_table / local_file）
  → POST /api/v1/timetables/uploads
  → 成功：进入「我的上传」列表（数据来自服务端 uploads/mine）
```

**注意：上传不等于落一份本机课表。** 提交后审核通过，发布后的版本回到详情页，用户可随时导入。客户端「我的上传」页的数据来自服务端 `uploads/mine`，不依赖本地课表存储。

**两种来源的取数路径：**

| 来源 | 客户端取数 | 提示 |
|---|---|---|
| 从本机课程表导入 | 读当前 `activeTable()` 的 courses（`CourseStorage.loadCourses`），逐条转成服务端 7 键 | 若当前课表为空 → 提示「当前课表还没有课程，先添加后再上传」 |
| 从本机导出的文件导入 | `course_transfer_service` 导出的 `xiyuan.course.tables` JSON（formatVersion 1），解析出 tables[].courses | 文件格式不符 → 提示「这不是掌上锡院导出的课表文件」；多表时选一张上传 |

两条路径都不允许手工拼课程行 —— 用户上传的必须是**已经存在于本机的真实课表**，这直接保证了审核内容的可信度。

### 7.3 学期开始日期

在线课表带学年学期（`xnm`/`xqm`），可推出学期第 1 周的周一 → 作为 `semesterStart`。因为是用户从服务端看到的既定数据，标记 `semesterStartSource = srcUser`，**不再弹「请确认第 1 周」**（与 `_showNewTableImportDialog` 的处理一致）。

  - 状态列复用资源审核的 `resStatus()` 风格。
  - 操作列：`待审核` → 「审核」（跳详情页）；其他状态 → 「查看」。
- **底部说明**：「一致性由上传课表与教务基准课表逐门比对得出；低于 85% 需人工核对后再决定是否通过。同一班级的多次上传按版本保留，先到先审，审核通过的版本才会被客户端检索到。上传者按其填写的名称展示，平台只保留学号哈希用于识别重复提交，不存学号明文、不存真实姓名。」

### 8.3 审核详情（核心）

自上而下：

1. **发布队列提示条**（浅紫底，`--accent-weak`）：「审核通过后进入发布队列，异步发布，通常 1 分钟内生效。」—— 提醒审核员「通过」不等于「已上线」。
2. **归属卡**：学年 / 学院 / 专业 / 班级 四行。
3. **来源与上传者**：来源类型（从本机课程表导入 / 从本机导出的文件导入）、版本号、**上传者名称**（用户自填昵称，如「张同学」）+ 学号哈希前缀（仅用于识别重复提交，不对外展示）、提交时间。
4. **隐私自检**：服务端自动扫描结果（学号 / 姓名 / 手机号 三项，各带「未检出」标签），有命中则红条警示。
5. **并排比对表**：左「上传内容」，右「教务基准」，行对齐，差异高亮（详见 §6.5）。
   - 一致行 = 绿条 + 浅绿底（`--ok-weak`）；差异行 = 浅红底（`--warn-weak`）+ 左红条，差异字段单独标红。
   - 右栏另设「一致性摘要」（匹配数 + 差异条目）与「同班级其它上传」（v0 / v1 并列，先到先审）。
6. **汇总**（紫底 `--accent-weak`）：「共 28 门，匹配 26 门，差异 2 门（周次不一致 1、时间冲突 1）」+ 逐条差异明细。
7. **审核操作区**：
   - `通过并发布`（主按钮）
   - `驳回`（次按钮 → 展开：原因下拉 + 意见 textarea，**注明上限 500 字**，必填原因）
   - `下架已发布课表`（危险按钮，仅对已通过的有意义）
8. **操作留痕卡**：只读时间线（上传提交 / 一致性比对 / 隐私自检通过 / 管理员打开详情 / 审核动作），写入 `audit_logs`。

## 11. 边界与非目标

**本次不做：**
- 不做课表**编辑后自动同步回在线课表**（在线课表是快照，版本靠重新上传）。
- 不做**课表分享链接**（微信/QQ 转发形态），只做站内检索。
- 不做**教务直连代理**（锡院在线课表不代替教务实时数据；教务实时路径仍在「输入账密快速导入」里）。
- 不做**课表冲突的自动合并算法**（在线课表侧多份并存，按一致度排序；导入侧整表覆盖，不逐条合并）。
- 不支持 **PDF / 图片 OCR 作为上传来源**（P0 只保留本机课表与本机文件两种来源）。
- 不上传任何**个人身份信息**（学号/姓名/手机号/成绩）。

**边界与风险：**

| 风险 | 应对 |
|---|---|
| 用户上传**错误班级**的课表 | 归属四段必填 + 审核时与教务基准比对（班级课表一比对就知道错没错） |
| 用户填写的**上传者名称**含学号/手机号/真实姓名 | 客户端提交前自检 + 服务端正则拦截（6 位以上连续数字、11 位手机号）+ 审核人工复核 |
| 用户**忘记已有该班课表**，重复上传 | 同一提交者同班级同来源自动升版本；不同提交者并列保留，先到先审 |
| 锡院在线课表**过期**（学期过了） | 审核端提供批量下架；客户端按学年学期默认只显示当前学期 |
| 同一班级**互相矛盾**的多份课表 | 不隐藏，全部展示，标一致度，按一致度排序，让用户自己判断 |
| 审核**积压** | 来源只有两种且都是本机真实课表，审核员只需比对结构与一致性，不需要下载附件 |
| 导入**覆盖**掉用户已有的班级课表 | 覆盖前必须弹差异明细（新增/变更/移除），按钮文案用「覆盖并导入」；只覆盖 `kindImported` 同名表，**不碰 `kindOwn`** |
| 数据库**无版本机制** | 新表全部 `CREATE TABLE IF NOT EXISTS` + `_ensure_column` 增量迁移，与现网一致 |

## 12. 落地顺序建议

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P0 数据与后端** | 建 4 张表；写上传/检索/详情/我的上传 4 个客户端端点 + 4 个后台端点；发布 outbox worker | 可用接口 |
| **P1 客户端检索与导入** | 班级实体模型；「锡院在线课表」检索页（搜索栏置顶 + 学年学期可改）+ 详情页三段式 + 覆盖导入落库 | 能搜、能导（直接覆盖） |
| **P2 客户端上传** | 3 步向导（两种来源 + 上传者名称）+ 课程核对 + 提交；本地课程归一化 | 能交 |
| **P3 后台审核** | 新增 tab + 列表 + 详情比对 + 操作区 + 队列观测 | 能审 |
| **P4 我的上传与闭环** | 状态跟踪页、驳回重提、撤销、收藏、下架联动、导入课表面板新增「锡院在线课表」一行 | 闭环 |

**P0→P1 就能出价值**（只读 + 导入），P2/P3 才能形成「上传→审核→发布」完整闭环。
